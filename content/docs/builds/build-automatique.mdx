Une **configuration de build** (BuildConfiguration) décrit **comment** et **quand** Nubiecloud construit une image à partir d'un dépôt. C'est ce qui transforme chaque `git push` en nouvelle image — sans intervention manuelle.

> 💡 Un même dépôt peut avoir **plusieurs configurations** (par exemple `frontend` et `backend` dans un monorepo), chacune avec ses propres règles.

## Paramètres de build

| Champ | Défaut | Rôle |
|-------|--------|------|
| **Nom** | — | nom de la configuration (ex. `backend`) |
| **Configuration par défaut** | non | la configuration utilisée par défaut pour ce dépôt |
| **Stratégie** | `dockerfile` | `dockerfile` ou `buildpack` |
| **Dossier source** | `.` | sous-dossier à builder (monorepo) |
| **Chemin du Dockerfile** | `./Dockerfile` | emplacement du Dockerfile |
| **Image builder** | — | image de build Buildpacks (stratégie buildpack) |

## Image produite

| Champ | Défaut | Rôle |
|-------|--------|------|
| **Nom d'image** | nom du dépôt | nom personnalisé de l'image |
| **Motif de tag** | `latest` | ex. `latest`, `{branch}`, `{sha}`, `{branch}-{date}-{sha}` |
| **Variables de build** | — | variables/arguments disponibles pendant le build |

Les variables disponibles dans le motif de tag sont `{branch}`, `{sha}`, `{date}` et `{name}` (le nom de la configuration de build).

> ⚠️ **Avec le build automatique activé, le motif doit contenir `{sha}` et `{date}`.** Sans ça, la configuration est refusée. La raison : un tag réutilisé (`latest`) est ambigu — impossible de savoir quelle version tourne réellement, ni de revenir à la précédente. Un tag **immuable** comme `{branch}-{date}-{sha}` identifie sans équivoque un commit et rend le rollback fiable.

> 💡 **Monorepo** : ajoutez `{name}` au motif pour distinguer les images de chaque configuration (ex. `{name}-{branch}-{date}-{sha}`).

## Déclencheurs automatiques

| Champ | Défaut | Déclenche un build sur… |
|-------|:------:|--------------------------|
| **Build automatique activé** | non | (interrupteur général) |
| **Sur push** | oui | un `git push` |
| **Sur tag** | non | la création d'un tag |
| **Sur pull request** | non | l'ouverture/mise à jour d'une PR |

## Filtres

Pour ne builder que ce qui compte :

| Filtre | Exemple | Effet |
|--------|---------|-------|
| **Filtre de branche** | `main,develop` ou `feature/*` | ne builder que ces branches |
| **Filtre de chemin** | `frontend/**,shared/**` | ne builder que si ces chemins changent (idéal monorepo) |

> 💡 **Monorepo** : combinez **Dossier source** (`services/api`), **Filtre de chemin** (`services/api/**`) et un **Nom d'image** dédié pour builder chaque service indépendamment.

## Déploiement automatique (optionnel)

| Champ | Défaut | Rôle |
|-------|--------|------|
| **Déploiement auto activé** | non | déployer automatiquement après un build réussi |
| **Environnement cible** | — | l'environnement où déployer |

Activé, un push déclenche : **build → image → déploiement** dans l'environnement choisi, sans intervention.
